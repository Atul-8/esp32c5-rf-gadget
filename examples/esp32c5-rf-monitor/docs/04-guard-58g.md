# 任务 4：5.8G 频段守卫（`feat/4-guard-58g`）

> 本文件是阶段 4 的验收材料。三件事都做了，也都在真板（COM56）上跑过：
>
> * **不误报**：空环境 45 s 轮扫 → 只剩 1 条，而且是**本振杂散**（判成「持续单频点」），
>   不是「持续窄带」；第一版没有直流缺口时同一环境报了 13 条假「持续窄带」，根因见 §5.1。
> * **抓得到**：手上没有真 5.8G 图传，用 **回放注入**（真板录的噪声底 + 合成信号）自证，
>   5795 MHz / 4 MHz 宽 / +25 码 → 抓到 4.0 MHz / 96% 占空比 / 持续 9.4 s（§6）。
> * **要交代的边界**：5895–5925 MHz 测不到（芯片上限）、跨窗跳频不追、帧是周期快照。

## 1. 做了什么

`modes/guard_58g.py`（单文件；未动 `core/`、未动其它模块）：

- 5700–5895 MHz 用 20 MHz 窗 / 14.58 MHz 步进重叠滑扫，共 **13 个窗**（首尾压边）。
- 每个窗留 40 帧环形缓冲，判「**持续性**发射源」：时间均值频谱抬升 + 单帧占空比 + 连续帧数。
- 三类判词 + 两档持续性：`持续窄带` / `持续宽带` / `规律跳频` / `持续单频点` / `间歇单频点`。
- 告警日志：编号 `G58-NNN`、出现时间、频点、带宽、峰值抬升、占空比、持续时长、在发/已停。
- 告警首次出现时 `store.add_event("guard_58g", "alert", {...})` 落库（由 `app` 层注入 store，见 §4）。
- 输出 ASCII 表格 + 结构化 `web_payload()`（含 `thresholds`、每窗覆盖率、判据原文 `notes`）。

| 常量 | 值 | 依据 |

| `BAND_LO_HZ` / `BAND_HI_HZ` | 5700 / **5895** MHz | 任务书写 5700–5900，但 C5 调谐上限是 5895（`docs/rx-controls.md`），越界就是假数据 |

| `DWELL_MS` / `BINS` | 100 / 512 | 39.06 kHz/格 |
| 窗数 | 13（5710.0 → 5885.0） | 首窗左沿压 5700，末窗右沿压 5895 |

```bash
python -c "from modes.guard_58g import window_centers; c=window_centers(); print(len(c), [round(h/1e6,1) for h in c])"
# 13 [5710.0, 5724.6, 5739.2, 5753.8, 5768.3, 5782.9, 5797.5, 5812.1, 5826.7, 5841.2, 5855.8, 5870.4, 5885.0]
```

## 3. 判据（每条都对应一个具体失败现象）

| 判据 | 值 | 为什么是这个值 |
| --- | --- | --- |
| 单帧「亮着」 | 比该帧 p25 高 ≥ `OCC_EXCESS_DB`=6 码 | 逐帧取 p25 当参考，抗「半窗空半窗有信号」的台阶；p10 会被空窗拉低 |
| 时间均值抬升 | ≥ `ALERT_DB`=10 码 | 均值谱把噪声压掉一半以上，10 码 ≈ 明显高于底噪抖动 |
| 占空比 | ≥ `HOP_FILL`=0.20 才算「持续性」 | 偶发尖峰不该报警；低于 20% 的是路过，不是发射源 |
| 持续档位 | `STEADY_FILL`=0.75 | ≥75% 记「持续」，20–75% 记「规律跳频/间歇」 |
| 连续帧 | `MIN_FRAMES`=8 | 少于 8 帧的凸起是一次噪声事件，不写日志 |
| 段宽 | 100 kHz – 16 MHz | 比 16 MHz 宽的是 WiFi/宽带干扰，归 `wifi_check` 管 |
| 单频点 | ≤ `SPUR_MAX_HZ`=0.5 MHz | 实板环境里 0.1 MHz 级持续凸起就是本振/时钟杂散，和图传（≥1 MHz）必须分开 |
| 交替跳频 | 同窗两段占空比都在 0.20–0.75 且相关系数 ≤ `ALT_CORR`=-0.4 | 模拟图传跳频最像的形态：两个频点互斥出现 |
| 跨窗聚类 | 中心差 ≤ `MATCH_HZ`=6 MHz 视为同一源 | 重叠窗会把同一个源在相邻 2~3 个窗各看到一次，不聚类日志里就重复 N 遍 |
| 存活 | 最近 `STALE_S`=60 s 内没有新帧 → 标「已停」 | 环形缓冲里留着旧帧不等于源还在发（第一版就栽在这，§5.2） |

### 3.1 两个「不判」的区域（实板实测挖出来的）

| 区域 | 处理 | 证据 |
| --- | --- | --- |
| 窗中心 ±250 kHz | 一律不判 | 5740 / 5768 / 5450 MHz 三个频点、每个窗的正中心都有一根 **3 格宽、高出底噪 33~43 码**的尖峰，形状完全一样 → 接收机直流/LO 泄漏，不是环境里的信号 |
| 窗两侧各 0.5 MHz | 一律不判 | 20 MHz 窗靠边的滚降本身高出均值 10~27 码（5450 MHz 实测边缘 27 码） |

代价：正好落在窗中心 ±250 kHz 的发射源抓不到。可以接受——真实 5.8G 图传最窄也有 1 MHz，
不可能只占中心那 6 格。

## 4. 事件落库怎么接

`modes/` 不 import `core.store`。模块只在实例上留一个 `store` 槽位，由 **app 层**注入：

```python
# app/__init__.py
def bind_store(registry, store): ...   # 只给「自己声明了 store 属性」的模块挂上

# app/live.py / app/demo.py
bound = bind_store(registry, store)     # → ['guard_58g']
```

告警**首次出现**时写一条 `events`，续时长不重复写（避免每秒刷表）：

```text
入库：11192 行 → .data/guard/g58-kind.db
事件：guard_58g 1 条 → .data/guard/g58-kind.db
```

`events.payload` 是告警首次出现那一刻的快照（`duration_s` 因此是 0）；
要看**当前**持续时长请读产出表格或 `web_payload()["alerts"]`。

## 5. 真板实测（COM56 / 增益固定 60 / 45 s）

### 5.1 第一版：同一环境报 13 条假「持续窄带」

```text
| G58-001 | 在发 | 持续窄带 | 5725.0 | 0.1 | 38.4 | 98% | 0.1 |
| G58-002 | 在发 | 持续窄带 | 5739.0 | 0.2 | 31.4 | 93% | 0.0 |
| G58-003 | 在发 | 持续窄带 | 5754.0 | 0.1 | 25.1 | 86% | 0.0 |
...  共 13 条，频点逐个等于 13 个窗的中心
```

**根因**：`CENTER_NOTCH_HZ` 之前没有挖直流缺口，每个窗正中心那根 3 格尖峰都被当成发射源
（13 窗 → 13 条，频点 = 窗中心，占空比 86~98%）。

排查命令（`testing/` 之外的临时探针，逻辑已固化进 `tests/test_guard_58g.py::test_center_spike_ignored`）：

```text
== 5740 MHz / 20 MHz 窗 / 1024 bin ==
  bin  512  offset  +0.000 MHz  mean  106.2  excess  43.4
  bin  511  offset  -0.020 MHz  mean   98.0  excess  35.2
  bin  513  offset  +0.020 MHz  mean   96.3  excess  33.5
== 5768 MHz ==  bin 512 excess 42.4 ；== 5450 MHz ==  bin 512 excess 35.4
```

三个相隔 300 MHz 的频点、同一位置、同样 3 格宽 → 只能是接收机自己的直流/LO 泄漏。

### 5.2 第二版：13 条 → 2 条，且都是 0.1 MHz

挖掉直流缺口后剩 `5708.0` 与 `5776.0` 两条，宽度 0.1 MHz。把库里录到的原始谱挖出来看：

```text
窗 5710.0 MHz 帧 278  bin 512  p25 31.9  超 10 码的格数 6
  * bin  204 off  -2.031 MHz mean   55.7 excess   23.8
  * bin  205 off  -1.992 MHz mean   62.7 excess   30.8
  * bin  206 off  -1.953 MHz mean   46.0 excess   14.0
    bin  207 off  -1.914 MHz mean   33.5 excess    1.6   ← 隔壁立刻掉回底噪
```

3 格宽、两侧一格就掉回底噪、时间上持续 88~97% —— 这是**本振/时钟杂散**，不是图传。
所以不改判据门限，而是**新增类别**：≤0.5 MHz 记「单频点」，与「窄带」分开。

### 5.3 第三版（当前）：空环境只剩 1 条杂散

```text
[alert] 5.8G 频段守卫（5700–5895 MHz，告警 1 条）
| G58-001 | 在发 | 持续单频点 | 5776.1 | 0.2 | 25.7 | 88% | 0.0 | 23:49:36 |
调度统计（245 片 / 3682 帧(本模块) / 44.8 s，错误 0）
```

结论（如实）：**这个房间里没有 5.8G 图传**。空环境误报 = 1 条杂散（且已单独归类）。
真板这一组只能证明「不误报」，证明不了「真来了能抓到」——那是 §6 回放注入的活。

## 6. 灵敏度自证：回放注入（`testing/guard_replay.py`）

做法：读真板录下的 snapshot（真噪声底、真时间戳、真前端形状），在指定频点注一段
`width` 宽、抬 `lift` 码的平顶，再喂给 `Guard58G`。抓到就说明判据没把真信号挡在门外。

```bash
python testing/guard_replay.py --db .data/guard/g58-kind.db
```

| 注入 | 结果 | 判读 |
| --- | --- | --- |
| 5795 MHz / 4 MHz / +25 码 | ✅ `持续窄带`，中心 5795.0、带宽 **4.0**、抬升 30.5、占空比 96%、持续 9.4 s / 40 帧 | 频点、带宽、时长三项都准 |
| 5720 MHz / 8 MHz / +20 码 | ✅ `持续窄带`，中心 5720.0、带宽 **8.0**、占空比 91%、持续 10.0 s | 宽带图传也认得 |
| 5830 MHz / 2 MHz / +12 码 | ✅ 抓到，但带宽估成 **0.9 MHz**、抬升 16.9 | 弱信号下只有中心几格过门 → **宽度会低估**，这是边界不是 bug |
| 5880 MHz / 4 MHz / +8 码 | ❌ 只报出一根 0.1 MHz 单频点 | **+8 码低于 `ALERT_DB`(10) → 按设计漏报**；灵敏度下限 ≈ +10 码 |

退出码 0/1 可直接进 CI。四条实测输出都是本机真跑出来的（库 = 上面 §5.3 那份 44.8 s 数据）。

## 7. 上位机

`host/web/pages/raw/page.html` 是通用兜底页，**任何模块的 `Output` 都会被它渲染**，
所以 `guard_58g` 的告警表现在就能在 GUI 的「原始输出」页看到，含判据原文 `notes`。
本轮没有再单开一个 5.8G 专属页面（任务 4 的交付面是模块 + 告警日志 + 落库，不是新页面）；
需要时照 `pages/ble/` 的结构加一页即可，`web_payload()` 里的 `thresholds`/`alerts`
已经按「前端零硬编码」的口径准备好了。

## 9. 没做的事（都记在 `todo.md`）

- **跨窗跳频不追**：只判同一 20 MHz 窗内两个频点交替；一步跳 >15 MHz 的源会跨窗，本模块不追
  （要追得靠固件侧连续 IQ，那是任务 5 的抓档口径）。
- **5895–5925 MHz 未覆盖**：芯片调谐上限，不是没扫。
- **不做设备归因**：只看「有个持续的、多宽、多久」，看不出「这是哪个牌子的摄像头」。
- **宽度在弱信号下会低估**（§6 第 3 行），已写进边界。
- **没有真实 5.8G 发射器**做正样本验收：只能回放注入自证；等有实物再补一条真信号实测。
