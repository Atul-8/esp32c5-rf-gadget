# 任务 2：周期性频谱瀑布图（`feat/2-waterfall`）

> **边界声明（产出物上也有，这里再说一遍）**
>
> * **周期快照，非连续实时** —— 单射频分时扫描，扫完一个窗就跳到下一个窗，
>   帧与帧之间存在接收空档；图上的"行"是**扫到过的**功率码，不是连续采样。
> * 功率码是**相对 dB 码（0..255）**，**不是 dBm**；色标只表示相对强弱。
> * 时间分辨率 = 一轮轮扫的时长（44 窗 × 100 ms ≈ **4.4 s**），比这更快的起伏看不见。

## 1. 目标与判据（任务书原文）

| 任务书要求 | 本实现 |
| --- | --- |
| 周期性全频段轮扫（2.4G ISM / 5G 低段 / 5G 高段） | `modes/waterfall.py: sweep_plan()`，一轮 44 个窗 |
| 快照顺路入库，不额外占用扫描时间 | `on_snapshot()` 只计数 + 进环形缓冲；入库由 `Scheduler` 顺路写 SQLite |
| 从 `Store` 读历史渲时频热力图（PNG + HTML） | `output/heatmap.py`（手写 PNG 编码器 + HTML 翻页） |
| 横轴频率、纵轴时间、数小时可翻页 | 每页 300 s，一页一个 PNG，`index.html` 列页目录 |
| 产出物标注「周期快照，非连续实时」 | PNG 页眉英文 + HTML banner + 页脚 + CLI 打印，四处 |
| mock 跑 10 分钟 → 肉眼能分辨 WiFi 突发块与微波炉宽带噪声 | 见 §5 实测（`microwave` 与 `mixed` 各一套） |

## 2. 轮扫计划

窗口参数沿用任务 1 已定的用户裁决（20 MHz 窗 / 15 MHz 步进），三频段首尾都压边：

| 频段 | 覆盖 | 窗数 | 相邻窗步进 |
| --- | --- | --- | --- |
| `24g` 2.4G ISM | 2400.0 – 2483.5 MHz | 6 | 12.7 MHz（均分，≤15） |
| `5gl` 5G LOW | 5150 – 5350 MHz | 13 | 15.0 MHz |
| `5gh` 5G HIGH | 5470 – 5850 MHz | 25 | 15.0 MHz |

一轮 = 44 窗 × 100 ms 驻留 ≈ **4.4 s**。

> 为什么"均分"而不是"按 15 MHz 走到底再补一窗"：后者在 2.4G 会留下 18.5 MHz 的
> 最后一跳（窗仍是重叠的，但步进超了口径）。均分后每跳 ≤ 15 MHz，边界仍压死。

## 3. 一个关键决定：**一行 = 一轮轮扫**（不是 1 s）

第一版按"1 s 一个时间桶"切行，结果图上是**满屏竖条纹**：一轮 4.4 s，1 s 的桶里
只装得下 44 个窗里的 9~10 个，其余列这一行根本没扫到 → 大面积"0 码"空洞。

改成**按轮分组**：

```text
group_sweeps(snapshots)   # center_hz 相对上一帧变小 = 换了一轮
```

三个频段的窗口都是升序，`5850 → 2410` 一定回卷，所以"中心频点回卷"就是轮边界。
好处：

* 每行都是**这一轮真的扫到过**的完整频谱，没有假空洞；
* 真机上驻留时间有 ±ms 抖动也不影响分组（不依赖时钟，只看频点序列）；
* 行数 = 轮数，10 分钟 ≈ 136 行，5 分钟/页 ≈ 69 行，图的高度自然合适。

保护：单轮帧数上限 `SWEEP_FRAME_LIMIT = 4096`，防某个频段数据永远不回卷时行数失控。

## 4. 渲染规则

| 项 | 规则 |
| --- | --- |
| 列 | 频率格：每频段固定 720 格，等宽显示，刻度按各自跨度标（2.4G 约 0.116 MHz/格） |
| 行 | 一轮轮扫（≈4.4 s），自上而下递增 |
| 同格多窗覆盖 | **最大保持**（窄带峰不会被相邻窗摊平，也顺带抵掉重叠滑扫的双计） |
| 没扫到 | 0 码，渲成最暗色；HTML 页脚写明"一行内不同频段的采样时刻并不相同" |
| 色标 | 冷→热 7 段，范围取**本页**非零码的 min..max（打印在色标两端） |
| 像素保真 | 刻度/文字只画在边距里，**不覆盖数据像素**（有测试逐行比对 PNG 像素与矩阵） |
| 文字 | PNG 里只有 ASCII（5×7 点阵），中文一律落 HTML —— 不引第三方字体/图像库 |

依赖：**零第三方库**（`zlib` + `struct` 手写 PNG）。本机无 PIL/numpy/matplotlib，
这是硬约束，也是 `output/png.py` 存在的原因。

### 5.1 图里能看出什么（列均值，页 1，2.4G 频段）

| --- | --- | --- | --- |

| 2437 MHz | 98.9 | **22 / 137** | 51 / 18（WiFi 突发：有亮有暗） |

| 2455 MHz | 66.5 | 25 / 78 | 62 / 7（微波炉宽带，均匀但不高） |
| 2470 MHz | 70.0 | 30 / 77 | 67 / 2 |

## 5.1 上位机侧的两个坑（2026-11 实测修掉）

真板跑 40 s 的自检里暴露了两个只有「多模块共享单射频 + 真机帧率」才会现形的问题：

1. **环形缓冲必须按「窗」存，不能按「帧」**。真板一次 `scan()` 回 30+ 帧，
   一帧一条的话默认 `RING_FRAMES=1200` 连一轮（44 窗 × ~37 帧 ≈ 1600 帧）都装不下，
   上位机永远只画得出一行半（实测 30 s → `rows=2`）。现在 `on_snapshot()` 对**同中心频率的连帧
   做最大保持合并**，缓冲粒度 = 窗 → 40 s 实测 `rows=5 / sweeps=5 / painted 100%`。
   `frames` 仍然数真帧（13170），别拿它当缓冲长度。
2. **`row_period_s` 只用「扫满」的轮次算**。环形缓冲截断最老那一轮时，残轮的时间戳会把
   周期算小（实测真板算出 1.8 s < 射频 4.4 s，逻辑上不可能）。现在只有 `len(sweep) >= windows`
   的轮次参与中位数；凑不齐两整轮就返回 `0.0`，前端退回射频时间。

另外 `slice_weight` 两边都是 `1.0`（`waterfall` 与 `wifi_check` 各占一半射频时间）：
原来是 0.8 vs 40.0，实测 share `{waterfall: 0.016, wifi_check: 0.984}`，
瀑布一轮 4.4 s 的射频时间被拉成 5 分钟——「看起来没数据」其实是饿死，不是 bug。

## 7. 未覆盖 / 已知限制（不许美化）

1. **没上真机跑瀑布图**：本分支只做宿主侧；`app.waterfall` 目前只有 mock 源。
   真机用 `app.live.py`（任务 1 已验）扫出来的数据同样走 `Store`，接口一致但**未实测**。
2. **虚拟时间压缩**：10 分钟数据 40~50 s 生成，图上时间轴是"等效时间"，不是墙钟。
3. **mock 的逐 bin 抖动**：`SpectrumSynthesizer._is_on()` 是按 bin 掷骰子的，
   同一帧里一个 duty=0.6 的源会一半 bin 亮一半暗；真实信号不会这样。
   所以图上的"噪点感"是 mock 特性，不是渲染 bug（真机数据会更"干净"）。
4. **单射频分时**：同一行里三个频段的采样时刻不同，2.4G 与 5G HIGH 之间隔了 3 秒多。
5. **色标是相对码**：同一页内可比，跨页/跨场景不可比（每页各自归一）。
6. **渲染性能**：720×69×3 频段的逐像素 Python 循环，一页约 0.3 s；小时级（12 页）约 4 s，
   可接受；若要做到 24 h 需要行级缓存或 numpy。
7. **上位机页面已在 `feat/host-gui` 落地**：`host/web/pages/waterfall/`（注册表一行 + 片段 +`js/pages/waterfall.js`），
   数据来自本模块的 `web_payload()`（`kind="waterfall"`，一行 = 一轮、一格一字节 base64、0 码 = 未扫到）。
   本分支（`feat/2-waterfall`）没有 `host/` 目录，两分支合并后才看得到页面。
8. **上位机染色口径（2026-11 真板报障后修正）**：每段以**本段 p10 底噪**为颜色 0 点、
   高出 30 码即满亮（`waterfall.js` 的 `SPAN_CODES`）。老实现按 p5..p95 两端拉伸，
   一段里只要有强信号，p95 就被抬到信号上、底噪全压到最暗 —— 真板 5G HIGH 底噪 29 码、
   峰 186 码，于是整段看着像"没扫到"。段标题旁同时标出 `底噪 N · 峰 M`，
   "没数据"（写「本段暂无可视数据」）和"数据太暗"一眼就能分开。
9. **没有扫满的轮次也画**：老实现一轮没扫满就只画最后一行 = 当前轮，而窗按频率顺序扫、
   高段排在最后 → 那一行的高段永远是空的（真板实测就是这个现象）。
   现在改为画最近**两**行并在 payload 里给 `degraded: true`，高段上一轮的数据就能显示。
10. **上位机上的窗口时间尺度很短**：GUI 只画环形缓冲里的最近记录（按窗存，默认 1200 窗 ≈ 27 轮 ≈ 5 分钟），
   小时级历史仍要走 `app/waterfall.py` 读 SQLite；两边口径相同但不共用同一份数据。
