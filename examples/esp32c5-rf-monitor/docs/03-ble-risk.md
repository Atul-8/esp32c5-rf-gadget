# 功能 3：BLE 广播信道风险评估（feat/3-ble-risk）

> 本文件是阶段 3 的验收材料。mock 侧 8 个场景全跑过；判决逻辑用**合成功率**逐档佐证
> （第 4.1 节，`python tests/sim_ble_verdict.py`）；实板侧在 COM56 上做了一组
> **只改增益**的对照实验（20/40/60 三档），把「环境占用」和「前端动态范围」分开，
> 第 6 节原样交代，没有拿 mock 数字冒充实板数字。

## 1. 做了什么

`modes/ble_risk.py`（单文件，未动 `core/`、未动其它模块）：

- 扫 BLE 全部 40 个信道的频段：3 个广播信道 **2402 / 2426 / 2480 MHz** 各用一个窗中心对准，
  数据信道区 2404–2478 MHz 用 20 MHz 窗 / 15 MHz 步进重叠滑扫，共 **8 个窗**。
- 逐窗判「这次有没有信号」「这个信号是不是窄带凸起」，聚合成广播信道活动占空、
  窄带突出度、覆盖率，再算拥挤评分与风险类型。
- 判词六档：`无明显风险` / `轻微干扰` / `复杂噪音（多源混合）` / `蓝牙设备密度型` /
  `WiFi 压制型` / `宽带常开/形状疑似`（+ `混合型`、`无数据` 两个过渡档）。
- 输出：ASCII 表格（4 行：3 个广播信道 + 数据区）+ 结构化 `web_payload()`（含 `evidence`
  证据链）+ 共存建议 + 前端余量告警。

## 2. 扫描计划

| 常量 | 值 | 依据 |
| --- | --- | --- |
| `SCAN_BW_HZ` | 20 MHz | 与功能 1 同一套口径（20 MS/s 整窗有效通带） |
| `USABLE_HALF_HZ` | ±10 MHz | 同上，窗外 0 码不参与判读 |
| `SCAN_STEP_HZ` | 15 MHz | 相邻窗重叠 5 MHz，数据区不留空洞 |
| `DWELL_MS` | 100 | 20 MHz / 1024 bin ⇒ 19.5 kHz 分辨率 |
| 窗数 | 8（2402/2414/2426/2429/2444/2459/2468/2480） | 3 个广播信道**中心对准**（要干净的肩部）+ 数据区 5 窗 |

```bash
python -c "from modes.ble_risk import scan_plan; print([f'{hz/1e6:.0f}' for hz in scan_plan()])"
# ['2402', '2414', '2426', '2429', '2444', '2459', '2468', '2480']
```

**为什么广播信道必须中心对准**：判据要拿 ±4~8 MHz 的肩部当参照，窗偏了肩部就一侧出窗、
一侧撞上邻道，凸起量算不准（这是第一版被 mock 抓出来的）。

## 3. 判据三原则（每条都是踩坑换来的）

### ① 电平取 **p80**，不取中位数

BLE 是 2 MHz 通道里的短脉冲，**不铺满整个 2 MHz**。中位数会被「没有脉冲的那一半 bin」
拉回底噪，导致强 BLE 也读成安静。实测：`ble_crowded` 场景中位数口径给 37% 活动、
p80 口径给 100% 活动，后者与场景注入一致（3 台强 BLE 常开广播）。

### ② 窄带占比门槛 ≥ `NARROW_RATIO`(50%)

只判「比肩部高 8 dB」不够：WiFi 的 20 MHz 梯形斜坡扫过广播信道时，
**一侧肩部低、一侧肩部高**，通道电平照样比肩部高十几 dB，会被误判成窄带凸起。
所以要求窄带凸起量 **≥ 本次抬升的 50%**：

```
rise   = level_p80 - ref            # 相对本帧底噪抬了多少
prom   = level_p80 - shoulder_p80   # 比肩部高多少
hit    = rise > 12 dB  and  prom > 8 dB  and  prom >= 0.50 * rise
```

### ③ 肩部取左右**各自 max**，不合并

两侧不对称（正是 WiFi 信道边缘扫过广播信道的形态）时，把左右肩部先合并再取中位，
会让参照电平跳变、台面被低估 → 又把 WiFi 斜坡算成窄带凸起。取 `max(left, right)`
（`_p80` 后取大者）后，`wifi_suppress_ble` 的假凸起从 88% 掉到 0%。

## 4. 判决口径（六档判词，先判「分不分得清」再判「是哪一类」）

```
证据链（每帧都算，产出时汇总）
  adv_activity      三个广播信道上「达标窄带命中」的帧占比
  shallow           「浅抬升」帧占比：抬升在 (4, 12] dB 之间（有东西、但没到判定门限）
  wideband          时间均值频谱里，ISM 内高于 floor+10 dB 的频点占比
  contrast_db       抬升频点在**时间上**的开关幅度（p80），减去安静频点的抖动
  slots / 常亮栅格  数据区 37 个 2 MHz 栅格的平均活跃数 / 「≥80% 帧都亮」的常亮点
  rise_floor        本机噪声自己的抬升零点（p80−p10 的 p10），判据的 0 点

判词（顺序即优先级）
  无任何有效帧                                  → 无数据
  宽带占用 ≥ 50% 且 开关幅度 < 8 码             → 宽带常开/形状疑似（不许冒认 WiFi）
  宽带占用 ≥ 50% 且 广播活动 ≥ 15%              → 混合型
  宽带占用 ≥ 50%                                → WiFi 压制型
  广播活动 ≥ 10%                                → 蓝牙设备密度型
  剩下的证据类数 ≥ 2（浅宽带/浅广播/栅格/常亮） → 复杂噪音（多源混合）
  证据类数 = 1                                  → 轻微干扰
  证据类数 = 0                                  → 无明显风险
```

**为什么必须是这条顺序**（每一条都是被实际数据打回来的）：

1. **`rise_floor` 必须实测标定，不能写死门槛。** 纯噪声下 `p80−p10` 本来就有 6~8 dB。
   首版拿绝对 4 dB 当「浅抬升」下界，`quiet` 直接被判成「轻微干扰」——完全安静的底噪
   和浅干扰必须靠**本机噪声自己的抬升零点**才分得开。
   零点样本还要把**数据区 37 个栅格**一起算进去：广播信道全被占时（`ble_crowded`），
   只统计广播信道会把零点顶到 64 码，真实信号反而「没有抬升」。
2. **「宽带」不等于「WiFi」。** 前端滤波器的固定起伏也能让 80% 以上的频点高于底噪。
   区分靠 `contrast_db`：形状在时间上**一动不动**，信号会开关。整段一起上下动
   （增益/底噪在动，物理上不是信号）也判「分不清」，宁可不判。
3. **浅干扰必须自成一档。** 只有浅抬升、没有达标命中时判「轻微干扰」而不是
   「无明显风险」——「完全安静」和「有东西在动但还不够定性」是两件事，
   混成一档等于把输出逻辑做残了。
4. **多类证据同时成立时不给单一归因。** 常亮 CW（常亮栅格）+ 浅宽带 + 浅广播同时出现
   ⇒「复杂噪音（多源混合）」，而不是硬塞进 WiFi 或 BLE。

- `宽带占用率`、`contrast_db` **在时间均值频谱上算**，不在单帧上算。实板单帧噪声底跨 bin
  抖动很大（实测 p10≈20 / p50≈28 / p90≈41），固定门限 `p10+10` 会让 **37%** 的纯噪声 bin
  越线，安静环境直接被判成「2.4G 全被占」。多帧取均值后抖动按 1/√N 收敛。
- WiFi 共存判读用**双半宽**：测电平只取 ±9 MHz（`WIFI_MEASURE_HALF_HZ`，避开邻道泄漏），
  判重叠按 ±10 MHz 几何（`WIFI_SPAN_HALF_HZ`）；「在用」的判据是 18 MHz 窗口里
  ≥50% 的频点高于本帧 p10+8 dB（窄带 BLE 只占 2/18 ≈ 11%，用比例才分得开）。
- **前端余量告警**（`headroom_warning`）：每帧 p10 参考码 ≥ `HEADROOM_CODES`(12) 时，
  说明底噪已被增益抬起，宽带占用率**会随增益变化** —— 实板同环境实测增益 20/40/60
  → 宽带占用 27%/61%/85%，判词从「复杂噪音」一路滑到「WiFi 压制型」。
  这时输出里明确写「先降两档增益复测：占用率不随增益走才是环境」。

**边界（写在 `notes()` 里，每次产出都带上）**：

- 只评概率，**不做设备级归因**（看不出「几台什么设备」）。
- 功率码是相对 dB 码，**不是 dBm**，绝不换算成功率/场强。
- 单射频分时扫描，帧与帧之间有接收空档。

### 6.1 同一个房间、同一个脚本，只改增益（这是本轮最关键的一组数）

| 增益档 | 时间片 | 快照 | 源错误 | 底噪参考码 | 广播活动 | 浅抬升 | 宽带占用 | 开关幅度 | 常亮栅格 | 判词 | 评分 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 60 | 193 | 9120 | 0 | 22.2 | 13.9% | 24% | **85.3%** | 26 | 8 | WiFi 压制型 | 47.3 |
| 40 | 150 | 7033 | 0 | 10.9 | 9.0% | 34% | **61.0%** | 32 | 1 | WiFi 压制型 | 40.7 |
| 20 | 153 | 7193 | 0 | 0.9 | 4.4% | 39% | **26.9%** | 25 | 0 | 复杂噪音（多源混合） | 29.0 |

**怎么读**（不做过度解释）：

- 链路本身是干净的：覆盖率 100%、源错误 0、无饱和（峰值码 144–156，远没到 255）。
- **宽带占用率随增益走**：20/40/60 → 27%/61%/85%。真正的环境占用不会因为增益变而变，
  所以这 85% 里有很大一部分是**前端动态范围/固有起伏**被高增益抬起来的结果，
  不能当成「这个房间 85% 的 2.4G 频段被占」。
- 增益 60 下 `headroom_warning` 会自己把这条话说出来（底噪参考码 22 ≥ 12）。
- 增益 20 下的 26.9% 也不能直接当环境真值（底噪贴 0 码时灵敏度不足，弱信号测不到）；
  正确姿势是**两档增益取一致的那部分**：40 与 20 的宽带占用都远低于 60，
  说明 60 那档的高占用主要是前端。
- 这里没有「安静房间」可清场复核（房间是活的）。安静侧能力由 mock `quiet`
  （宽带 0% / 广播 0% / 评分 4.9）和仿真六档（`python tests/sim_ble_verdict.py`）守。

### 6.2 前端固有起伏长什么样（24 帧、每桶 32 bin，`gain=60`，2442 MHz 窗）

```
偏移： +14 +13 +11  +9  +6  +3  +2  +0  +2  +6  +7 +11 +12 +14 +16 +15 +21 +21 +22 +23 +22 +23 +24 +23 +22 +27 +27 +26 +25 +23 +21 +20
时间抖动：43 41 40 40 39 39 40 39 40 40 42 40 40 40 42 55 58 42 42 43 43 42 43 45 47 43 43 42 43 43 42 42
```

- 频谱是一条平滑的「碗形」（两端高、中间低 20 多码），**成块的信道沿看不到** →
  这是前端/滤波器的固有形状，不是「13 个 WiFi 信道全在用」。
- 时间抖动几乎恒定（39–45），不随电平变化 → 那一批高频点不是「在开关的信号」。
- 结论：**高增益下的宽带占用数字只能横向自比（同一档增益比时间/场景），不能当绝对占用。**

### 6.2 上位机增益调控对这套指标的影响（`host/gain.py`，实板）

同一块板、同一房间，只改增益档位，逐档实测底噪（2440 MHz，每档一轮 35~40 帧取 p10 中位数）：

```
  0~30 档 : 0.0 码            35~45 档 : 6.0 / 6.0 / 8.5 码
 50~65 档 : 25.0 / 22.0 / 31.0 / 24.5 码     70~81 档 : 30.3 / 47.0 / 51.5 / 63.0 码
```

- 档位上限来自固件 `GAIN?`（实板回 `GAIN MANUAL 60 0 81 1`），不写死。
- **单帧 p10 不可当控制量**：同档同频点连扫 14 轮，单帧 p10 在 **0 ~ 73 码**之间跳；
  闭环因此取「一轮中位数 + 轮间指数平滑」，一轮只决策一次。
- 真板闭环：起始 60 档、目标 8 码、14 轮 → `60 → 58 → 56 → 54 → 52 → 50 → 48`，
  平滑底噪 `39.0 → 14.4`，每两轮一档（`AUTO_CONFIRM=2`）。第一版用 1.2 s 墙上时间
  做冷却，而实板一轮约 1.1 s → 每轮都被卡掉，14 轮只动一档（已修）。
- 对 BLE 判据的意义：`headroom_warning` 的门槛是「底噪参考码 ≥ 12」，所以**同一份数据
  换个档位，这条告警会翻转**。看 BLE 结论时必须一起看当时档位（界面上 `档 N · 实测 M ·
  底噪 X 码` 就是为这个）。

| `PluginContractTest` | `discover("modes")` 能找到、端到端跑通、`reset()` 清空、`slice_weight == 1.0`、频段跨度 |
| `MixedScenarioTest` | `mixed` 场景两类证据同时出现时的判读 |

**踩到的坑（已在测试里固化）**：

1. `run_scenario()` 有缓存，`test_reset_clears_everything` 直接拿缓存实例 `.reset()`
   会把后面的测试连坐清空（`unittest` 按类名字母序跑）→ reset 测试必须自建实例。
2. `rise_floor` 只统计广播信道时，`ble_crowded` 的零点被顶到 64 码，
   真实信号「没有抬升」→ 必须把数据区栅格一起纳入样本池。
3. 浅抬升门槛用绝对值（4 dB）会把纯噪声判成「轻微干扰」→ 必须减掉 `rise_floor`。
4. `contrast_db` 用两侧均值会被静止部分稀释 → 改 p80。

## 8. 单射频公平性

`slice_weight = 1.0`，与 `wifi_check` / `waterfall` 相同。
（META-0087：权重悬殊会让低权重模块在共享单射频时被饿死，实测过。）

## 9. 上位机页面（`host/web/pages/ble/`）

页面结构、`thresholds` 下发约定、判词不翻英文、自检 checks 见
`host/README.md` §BLE 风险评估页。这里只记三条与本模块强绑定的纪律：

1. **门槛只在模块里**：`ble_report()` 的 `thresholds` 一并下发，前端不许出现判据数字。
2. **判词/hints/notes 是中文原文**，界面只翻外壳，不翻判词（翻了就跟 CLI 对不上）。
3. **`notes()` 也是 payload 的一部分**：网页「判据与边界」直接显示模块自己的话，
   维护时改模块就够，不用去改网页文案。

## 10. 没做的事

- 不做设备级归因（MAC/厂商/数量），任务书也没要求。
- 不做 BLE 信道跳频图的还原（需要连续 IQ，单射频分时拿不到）。
- 不做 dBm 换算（硬件只给相对功率码，换算就是编数字）。
- **不做固件侧增益标定**：宽带占用率随增益走（第 6.1 节实测 27%/61%/85%），
  正确做法是两档增益一致的那部分才算环境。上位机给了**主机侧**自动闭环
  （把每轮底噪 p10 中位数压到目标码，见 `host/README.md` §增益调控 + 第 6.2 节），
  但那是「让读数横向可比」，不是「把 85% 换算成真环境占用」。
- 不做「清场基准」（先录一份空房间基线再比）——需要用户配合清场，未做。

## 11. 一句话结论（`verdict()`）

真板实测反馈：「给一堆数字，看不出到底有没有风险」——所以模块除了判词，还直接下发结论。
`BleRisk.verdict()` 返回三样东西：

| 字段 | 取值 | 用途 |
|------|------|------|
| `code` | `clear` / `light` / `complex` / `flat` / `ble` / `wifi` / `mixed` / `nodata` | 页面据此选文案模板（`i18n.js` 中英各一套） |
| `level` | `risk` / `watch` / `clear` / `nodata` | 页面据此上色 |
| `why` | 证据 + 门槛的平铺字典 | 模板里所有数字都从这里取 |

两条硬约束：

1. **`code` 由 `VERDICT_CODE[risk_type()]` 得出**，与判词同一张映射表 ⇒ 结论和判词不可能互相矛盾；
2. **`why` 里带门槛**（`adv_thr` / `wideband_frac` / `contrast_thr` / `light_ratio` / `min_adv_frames`…），
   页面不自己算判据、不写死数字，改门槛只改模块。

页面结论条三行：**结论**（有风险 / 有抬升但不够判 / 没证据 / 还没数据）+ **凭什么**（把决定性的
两条判据和实际值并排写）+ **接下来做什么**（可执行的一句）。自检里 `ble_verdict` 一项专门守这条：
结论句非空、档位合法、三行都填了，缺一即红。
